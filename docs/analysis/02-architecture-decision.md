# 架构决策 01：本地插件 vs 可部署网站

> 决策时间：调研定稿后。原则：慢、稳、可验证；数据格式与消费端解耦。
> 修订 v2（对齐颗粒度后）：**"总菜单"（共享索引）从"阶段二可选"升级为骨干**，理由见 [03-risk-report-and-discovery.md](03-risk-report-and-discovery.md)：一致性（每家商城不跑偏）+ 单点全面检索 + AI 风险报告共享，一石三鸟。

## 结论（先行）

**做成"本地 DSH 插件为客户端、共享总菜单为数据骨干、网站仅为展示窗口"的形态**：

1. **客户端 = 本地 DSH 插件**（`dsh plugin add <market-pkg>` 一键装入，UI 注册进 `settings.plugins.tab`，自带 client bundle）；本地直连爬取保留为**离线兜底**；
2. **数据骨干 = 共享总菜单**（GitHub 仓库 + Actions 每日生成 `plugins.json` / 日报 md / 历史快照），**所有用户商城读同一份** —— 一致的市场、一致的排行榜、一致的日报；AI 风险报告进入共享缓存（一次生成、所有人读）；
3. **网站形态 = GitHub Pages 静态站**（同一份 JSON 的另一种呈现），零服务器成本，作为发现入口与日报展示壳 —— **非必需**。

类比成熟生态：VSCode（本地客户端 + marketplace）、Homebrew（CLI + formulae 索引）、npm（CLI + registry）——**CLI/插件负责安装，中心索引负责聚合**，这是被反复验证的形态。

## 决定性事实

1. **安装永远发生在本地**：浏览器沙箱无法往 profile 写 pnpm 依赖，`dsh plugin add` 必须在本机执行。**真正的"一键安装"只有本地插件/CLI 能做**，网站最多给出可复制命令或下载 patch 文件（徒增摩擦）。
2. **本地插件可以带 UI**（已核实 `dsh-client-modules`）：包声明 `dsh.client` + 导出 `./client` bundle → web 服务器自动发现该 loader 条目、注入 `__DSH_BOOT__` 清单、浏览器端加载 bundle 并注册 factory。无需改 DSH 本体；宿主侧服务可用 `ctx.webServer.register` 暴露同源路由（绕开 api-proxy 白名单问题）。
3. **集中索引解决三个纯本地解决不了的问题**：GitHub 搜索 API 未认证限流（60 req/h/IP，1800+ 仓库逐用户爬不现实）、趋势/排行榜冷启动（本地快照从安装当天才开始积累）、跨用户"全网热度"（纯本地算不出）。

## 两案对比

| 维度 | 本地插件（主） | 可部署网站（次/壳） |
|---|---|---|
| 一键安装 | ✅ 原生：复用 `dsh plugin add` + 显式确认 | ❌ 只能给命令/下载 patch；需本地桥接 |
| 已装插件感知 | ✅ 有 inventory（loader 状态、profile 位置） | ❌ 无，除非装本地上报组件 |
| 数据抓取 | 逐用户爬：限流、重复劳动 | ✅ 一个 crawler（可带 token），全量同步 |
| 热度/排行 | 冷启动慢；只有自己数据 | ✅ 全网即时；跨用户统计（注意隐私） |
| 每日日报 | ✅ cordis-plugin-timer 本地生成；但依赖本机开着 | ✅ 服务器定时生成，可靠；可订阅/邮件 |
| 开发成本 | 中（cordis 插件 + client bundle 双半） | 中（前端 + 后端/静态生成） |
| 运维成本 | 零 | 有（即使静态也要托管与更新流程） |
| 安全面 | 符合 DSH user-approval 理念；无第三方中间人 | 网站本身是钓鱼风险点，需锚定官方源 |
| 触达 | 已装 DSH 的用户 | 未装 DSH 的潜在用户（发现入口） |
| 生态惯例 | ✅ 与主流模式一致（topic + 装进 profile） | ❌ 无先例 |

## 推荐架构（演进式）

```
阶段一（本地优先，零基础设施起步）：
  本地插件 ──（优先）拉取共享总菜单 / （兜底）直爬 GitHub topic + npm ──> 本地缓存
     ├─ UI：settings.plugins.tab（自带 client bundle）
     ├─ 一键安装：dsh plugin add + 显式确认
     ├─ AI 风险报告：用户点开详情时用本机模型生成 + 本地缓存（见 03）
     └─ 日报：cordis-plugin-timer 每日聚合（本地生成）

阶段二（总菜单上线，网站变静态壳）：
  GitHub 仓库（如 plgstore/index）
    └─ Actions 每日：爬全量 → plugins.json + daily-report.md + history/*.json
         ├─ 本地插件 ──拉取 raw.githubusercontent──> 同一份数据（只读缓存；含共享风险报告）
         └─ GitHub Pages 静态站 ──渲染同一份 JSON──> 浏览/排行/日报
```

**关键设计决策**：Step 1 就把"索引 schema"定义为**中心化友好的**（来源、版本、验证状态、时间戳、风险报告槽位），阶段二只是把"谁生成这份 JSON"从用户本机换到 Actions，**消费端零改动**。这正是路线图里"索引可重建、schema 与消费端解耦"的用意。

## 中心化的代价（如实记录，决策留痕）

- 需要维护者跑 Actions + token（GitHub 免费额度内）；
- 用户需信任集中索引 —— 仅元数据 + 链接 + 文本报告，**非代码**，风险低；每条保留原始来源链接可自查；
- 若无人愿意运营 → 退回"阶段一 + 个人自建索引"，架构不变（生成端可换）。

## 对路线图的影响

- Step 1–6 顺序**不变**（先本地插件，但 schema 按"总菜单"设计）；
- Step 2 验收标准新增：**索引 schema 必须能被本地与中心两种生成端共享，且含风险报告槽位**；
- Step 5 日报先在本地生成，阶段二时把生成逻辑原样搬进 Actions；
- 新增 Step 2.5 候选：发现策略实现（多源并集 + 去重 + 来源标注，见 03）。
