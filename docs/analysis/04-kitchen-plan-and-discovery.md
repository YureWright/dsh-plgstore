# 厨房启动计划 + 插件发现策略（"又准又全"设计）

> 原则：先本地试做 → 验证菜谱 → 再开张到 GitHub。发现策略是产品创新的核心之一。
> 状态：设计稿。所有"需验证"项标注，待网络可用时逐一核实。

## 一、目标与验收（先定义"准"和"全"）

诚实前提：**绝对"又准又全"不存在**（生态在流动、来源碎片化）。目标是三个可量化指标：

1. **准（误报可控）**：进菜单的条目 ≥95% 是真插件（不是教程、清单、脚本、同名杂物）；抽查误报率 <5%。
2. **全（官方全覆盖 + 新货当日见）**：
   - 官方 monorepo 插件 **100%** 覆盖；
   - 已发布到 npm 的插件 **当日**进入候选池（不依赖任何标签）；
   - 与社区精选清单（awesome 系）对比，漏报 <10%。
3. **可重建**：任何一天重跑生成流程，产出与当天一致（幂等/可复现）。

## 二、核心洞察：现在的找法像"等招牌"，咱们改成"认身份证 + 蹲产房"

### 2.1 硬信号（身份证）——"准"的金标准

发现两个**官方结构化标记**（本地源码已核实，比话题标签可靠得多）：

| 信号 | 含义 | 强度 |
|---|---|---|
| package.json 声明 `dsh.bundle.patch` | 该包是 profile 层插件（装进 DSH 会参与层栈对账） | ★★★ 官方身份证 |
| package.json 声明 `dsh.client` + exports `./client` | 该包自带 Web UI 半侧 | ★★★ 官方身份证 |
| 依赖了 `@deepseek-ai/cordis` 或任一 `dsh-*` 核心包 | 装了 DSH 零件 → 几乎必是插件 | ★★☆ 强信号 |
| 包名/描述含 dsh / deepseek-harness / cordis | 弱信号（误报高，仅作候补） | ★☆☆ 弱信号 |

**"准"的机制**：不靠单一信号下结论，而是**多信号交叉打分**（见 §3），身份证级信号一票近通过，弱信号必须叠加才有效。

### 2.2 订阅式增量发现（蹲产房）——"全"的创新点

不做"每天全量重爬"（慢、限流、漏新货），而是**订阅两个"产房"**，让插件"出生当天"就被发现：

1. **npm 发布流**：npm 公开的变更流（`replicate.npmjs.com/registry/_changes`，CouchDB changes feed，**需验证当前可用性**）——凡是新发布/更新的包，立刻过滤"名字/描述含 dsh 或带 dsh 字段"的进候选池。**标签还没贴、列表还没收录，我们就已经知道了。**
2. **GitHub 新货架**：搜索 API 按 `created:>上次同步时间` 增量查询 `topic:dsh-plugin`（及关联 topic：`deepseek-harness`、`dsh`），只看新增。

> 补充：GitHub 搜索 API 单查询 1000 条上限 → 存量用**按创建时间分桶**补齐；code search（找 `"dsh.bundle"` 在 package.json 里）需 token，作为身份证信号的执行手段之一。

### 2.3 作者自荐（托关系）——补全长尾

GitHub issue 表单起步（VSCode/Homebrew 同款模式）：作者提交仓库/npm 包名 → 进候选池走同一套验证。**所有成熟生态的最后一块拼图都是这个。**

## 三、候选 → 菜单：三信号入选 + 质量分排序 + 验证闭环

> **2026-08-15 用户拍板修订**：入选不再靠分数门槛，改"三信号任一即入选"；分数改为质量提示与排序权重（见 menu-schema.md 决策 D7/D8）。

```
发现（五路进料：官方仓库 / topic / npm 发布流 / 精选清单 / 自荐）
   ↓
候选池（实体合并：GitHub 身份 ↔ npm 身份 → 一条记录，保留 sources[]）
   ↓
入选（D7：三信号任一即入选；三者皆无 → 不入选）：
   ① 有盖章（dsh.bundle / dsh.client 声明）
   ② 有依赖（依赖 @deepseek-ai/cordis 或 dsh-* 核心包）
   ③ 有标签（GitHub topic 含 dsh-plugin / deepseek-harness / dsh）
   官方仓库另按 D3（只收 bundle）
   ↓
安装方式（硬规则优先，LLM 兜底疑难，见 menu-schema.md §五·A）：
   npm 可确认 → npm；只有 GitHub → git；release 资产 → tarball
   ↓
质量分（D8：不设门槛，用于提示 + 推荐/排序靠后）：
   盖章 / 有 npm / 活跃更新 / README 完整 / AI 验货结论（LLM，按需）
   ↓
验货（AI 风险报告顺带做验证，Step 6 实现）：
   有 README + package.json → 通过，按信号强度分档
   连自我介绍都没有 → 判为假插件，出池
   ↓
菜单（plugins.json）：每条含 来源、信任层、质量分、安装信息、时间戳
   ↓
反馈回流：用户举报/安装反馈 → 更新状态（恶意/失效标记）→ 次日菜单生效
```

**闭环的意义**：发现 → 入选 → 验货 → 使用 → 反馈，各环节互相喂养。这是竞品都没有的。

## 三·五、行业对标：其他产品怎么检索插件（核实过的事实）

**最重要的认知修正：没有任何一家靠"爬全网自动发现"，全是"作者主动来 + 中央收录"。**

| 生态 | 模式 | 谁来"准" | 来源 |
|---|---|---|---|
| npm | **发布即收录**：任何人 `npm publish`，中央全收，不审核；搜索靠全文 + 流行度/质量/维护度打分排序 | 不审核（靠 npm audit + 社区信号） | 发布流即中央点 |
| VSCode / Chrome / Firefox | **提交 + 官方审核**（验证身份 + 恶意扫描） | 平台方审核团队 | 作者提交 |
| Homebrew | **PR 制人工审**：作者提 PR，维护者审完合进中央 formulae 清单 | 维护者人工审 | 作者提 PR |
| Obsidian（最像我们） | **PR 制中央 JSON**：[community-plugins.json](https://github.com/obsidianmd/obsidian-releases) 存在 GitHub 仓库里，作者提 PR + 人工 review，App 拉这份清单，插件本体走 GitHub 分发 | 维护者人工审 manifest | 作者提 PR |
| WordPress | 提交 + 自动/人工双重审核 + 开放 API | 平台审核 | 作者提交 |
| MCP 生态 | Smithery 等中央注册表，作者提交 + 一键安装 | 平台 | 作者提交 |
| **DSH 现状** | 自愿标签（topic）+ 人工清单（awesome）——**没有中央点** | 无人审核 | 标签/清单 |

**规律提炼（三种模式）**：
- **A 提交 + 官方审核**（VSCode/Chrome/WordPress）：最准最安全，但官方成本大、门槛高；
- **B PR 制中央清单**（Homebrew/Obsidian）：社区协作维护一份清单文件，轻量有序，**App 拉清单 + GitHub 分发** 正是我们设计的形态；
- **C 发布即收录、不审核**（npm）：最自由，质量靠打分信号与社区。
- **没有任何生态靠"爬全网"**：npm 的"中央点"就是发布流本身；GitHub-only 的生态（无中央点）只能靠标签 + 人工清单 + 作者自荐。

**对我们设计的再定位（重要）**：
1. 我们的"蹲产房"（订阅 npm 发布流）本质 = **订阅 npm 的中央点**——与 npm 自己收录的方式同构，不是异想天开；
2. "托关系"（作者自荐）= 所有成熟生态的**共同主干**（VSCode publish / Homebrew PR / Obsidian PR），不是可选项而是必经之路；
3. 我们真正的创新/妥协：成熟生态有**人工审核团队**（微软、Homebrew 维护者、Obsidian 维护者），我们没有 → **用"官方身份证信号 + 多信号打分 + AI 验货"替代人工审核**，并把"发现→验货→反馈"做成闭环；
4. 我们的厨房本质 = **给 DSH 生态补建缺失的中央点**（Obsidian 的 community-plugins.json 就是给 Obsidian 生态补建的）——产品定位由此更清晰：我们是 DSH 的 "community-plugins.json + 审核 + 日报"。

## 四、厨房启动计划（分阶段，不预建基础设施）

- **阶段 A（本地试做）**：在 plgstore 写抓取脚本（只读、幂等）——先抄官方 monorepo（本地即可枚举）+ GitHub topic 存量（分桶），落成 `plugins.json`；验证：能列/搜/排序、评分过滤生效、误报抽查达标。
- **阶段 B（验证增量）**：接入 npm 发布流（先验证 `_changes` 可用性；不可用则退化为"每日 npm 关键词搜索 + GitHub 新建搜索"），实现"当日发现"。
- **阶段 C（开张）**：把生成流程搬进 GitHub Actions（免费），产出 `plugins.json` + 日报 + 历史快照；本地插件与静态站消费同一份。
- **阶段 D（闭环）**：自荐表单、用户举报、AI 报告共享缓存（"买家评价"）。

## 五、风险与局限（如实记录）

- **绝对全做不到**：没人看过的自托管插件（不发布 npm、不贴标签、不自荐）永远发现不了——这是物理边界，写进文档不吹牛。
- **npm changes feed 可用性需验证**：若关闭，退化方案见阶段 B。
- **GitHub 限流与 1000 上限**：靠 token + 分桶 + 增量解决，中央厨房单点持有 token，比逐用户爬高效得多。
- **打分是启发式**：阈值需用抽查校准（阶段 A 就做），不追求"完美判真"，追求"误报可控、漏报有兜底"。
