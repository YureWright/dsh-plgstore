# 功能设计 01：AI 风险报告 + 插件发现策略

> 来源：用户讨论（对齐颗粒度后）。三件事其实是一件事：中央索引（"总菜单"）同时解决 一致性 / 全面检索 / 报告共享。

## 一、AI 全面评估报告（"老奶奶也能懂"的插件说明书）

### 目标（2026-08-15 修订：从"风险报告"升级为"全面评估报告"）
每个插件详情页配一份**全面评估报告**：既讲功能也讲风险；**大多数插件结论是"放心用，注意一二三点"**，少数明显可疑的才警告——不过度谨慎、不制造恐慌。

### 报告内容（直接吃 README）
- **intro 功能介绍**：这插件是干嘛的、能做什么（大白话，基于 README 概括）
- **risks 风险**：会碰电脑上哪些地方 / 哪些人可能看到什么
- **level 三档**：😊 放心用 / 🤔 留个心眼 / ⚠️ 别急着装
- **postInstallNotes 装后要点**：装完还要改配置/设环境变量等
- **notes 其他提醒**：如"经评估可能并非 DSH 插件（理由…）"、"疑似过期"等
- **classification 类型判断**：plugin/tutorial/list/script/other —— **只写进报告供参考，不决定入选**（入选由 D7 三规则负责；非插件/低信心进"存疑清单"供人工复查）

### 生成方式（厨房集中生成 + 共享缓存；本机模型为可选兜底）
> **2026-08-15 用户拍板（D10）**：LLM 由厨房自出（API 部署 GitHub Actions），集中生成、一次共享。
1. **主路径：厨房生成**——Actions 每日/按需调用厨房 LLM，产出评估报告写入共享缓存；所有用户读同一份，不重复花钱。
2. **兜底：用户本机模型**（可选）——共享报告缺失或用户想自己看时，用本机 DSH 配置的模型即时生成，结果只存本地。
3. 输入材料：README（自我介绍）+ package.json（依赖、是否有安装脚本/prepare）+ GitHub 元数据。**注意：README 抓取走 GitHub API（`/readme`、`/contents/package.json`），raw.githubusercontent 通道易被墙。**
4. 输出结构见上"报告内容"；**防循环论证**：仓库带 dsh-plugin 标签或自称 DSH 插件不算证据，必须有 package.json 声明/依赖/安装命令等真凭据。
5. 同一调用顺带产出 **install（安装方式）** 与 **classification（类型）**——LLM 的主要职责是"填充信息"，不是"筛选"。

### 校准原则（写进 prompt 与验收）
- 默认"放心"；只对以下信号升档：执行安装脚本、连接外部服务器、访问隐私文件/网络、来源不明、信息缺失。
- 页面上固定标注："**AI 生成的参考，非安全认证**"——报告是直觉不是安检，防止虚假安全感（对应官方讨论 #587 的信任缺口）。
- 报告与信任分层（官方 ✅ / 精选 🟡 / 待验证 ⚠️）是两套独立信号，都展示。

### 共享化（阶段二）
中央索引成熟后，报告进入共享缓存："买家评价"模式——一次生成、所有人读；用户可 opt-in 提交自己生成的报告（脱敏）。

## 二、插件发现策略（多源并集，追求"尽可能全"）

### 诚实前提
**没有单一来源能保证"全部"**；目标是"比任何单一来源都全"：多源并集 + 实体去重 + 来源标注。

| 来源 | 覆盖 | 手段与注意点 |
|---|---|---|
| 官方 monorepo（deepseek-ai/deepseek-harness） | 官方插件 100% | 解析 packages/ 目录或 dsh 依赖表（本地安装即可枚举 ~200 个） |
| GitHub topic `dsh-plugin` | 社区大头（1800+） | 搜索 API 分页；**注意单查询 1000 条上限 → 按创建时间分桶查询**；未认证限流 60 req/h（中央任务用 token） |
| npm 注册表 | npm 发布的插件（含不贴标签的） | 强信号：**依赖 `@deepseek-ai/cordis` / `dsh-*` 系的包**（依赖关系比话题标签可靠）+ 名称/描述含 dsh 关键词 |
| 社区精选清单（awesome 系） | 量小质高 | 当"验证/精选"层，不追求全 |
| 作者自助提交 | 补全长尾 | GitHub issue 表单起步（VSCode/Homebrew 同款模式） |

### 实体合并
同一插件在 GitHub / npm 各有一个身份 → 归一化为一条记录，保留 `sources[]` 标注"从哪发现的"，防止重复展示。

### 现状可行性
当前规模（几百~两千量级）每日全量同步负担得起；规模增长后靠"分桶查询 + 提交入口"兜底。

## 三、对架构决策 02 的修订

- **"总菜单"（共享索引）从"阶段二可选"升级为骨干**：GitHub 仓库 + Actions 每日生成 `plugins.json`（含元数据 + 风险报告缓存 + 历史快照），所有用户商城读同一份 → 一致性 + 报告共享 + 单点全面检索。
- **本地直连爬取降级为离线兜底**（索引不可达时）。
- 网站 = 菜单的另一个展示窗口（GitHub Pages 静态站），非必需。
- 不变量：Step 1 的"菜单格式"（索引 schema）必须中心化友好——生成端可在"用户本机"与"中央 Actions"之间无痛切换；本地插件按"读总菜单 + 兜底直爬"实现。
- 代价（如实记录）：需要维护者跑 Actions + token；用户信任集中索引（仅元数据+链接，非代码，风险低；保留原始来源链接可自查）。
