# 功能设计 02：反馈机制 + 评分机制（"买家评价"）

> 状态：设计稿。与 AI 风险报告（03）并列的第三套信号。原则：轻量防滥用，诚实标注未经人工审核。

## 一、定位：三套信号，各管一摊，别混

| 信号 | 谁产生 | 回答什么问题 | 示例 |
|---|---|---|---|
| 来源信任（信任分层） | 厨房（机器） | 它从哪来、靠不靠谱 | 官方 ✅ / 精选 🟡 / 待验证 ⚠️ |
| AI 风险报告 | 用户本机模型 | 它会不会害我 | "放心用 / 留个心眼 / 别急着装" |
| **用户反馈 + 评分** | 真人用户 | 它好不好用、有没有坑 | ⭐⭐⭐⭐ "装了会崩" |

三者独立展示，互不替代（一个官方出品也可能难用，一个社区小件也可能很香）。

## 二、身份基础：DSH 匿名身份证（已核实）

`@deepseek-ai/dsh-anonymous-user-id`：`getOrCreateAnonymousUserId()` 返回绑定单个 harness home 的随机 UUID v4，持久化于 `$DSH_HOME/.anonymous-user-id`（未设置 DSH_HOME 时为 `~/.dsh/.anonymous-user-id`）。
- **不**从 hostname/IP/git remote 派生 → 伪匿名、无需注册账号；
- 删除文件 = 换新身份（按设计如此）；
- 官方已用它做遥测与 `/feedback` 关联 —— **我们的评分/反馈直接复用同一身份**，与 DSH 生态一致。

## 三、反馈机制（问题上报）

**入口**（店面 UI + agent 工具，二选一或都做）：
- 插件详情页"报告问题"按钮：类型 = 装不上 / 用不了 / 可疑行为 / 内容失效；
- 顺带提交上下文：DSH 版本、插件版本、匿名身份、可选日志摘要（用户确认后才发）。

**通道（起步，最廉价）**：厨房仓库的 GitHub issue 表单（结构化模板）→ 厨房维护者/脚本把状态回流到菜单（标记"有报告"→ 攒够 N 条自动降级信任层）。

**关键约束**：反馈是"厨房收信"的第一个写通道 → 决定后续评分通道的技术选型（见 §五）。

## 四、评分机制（星级 + 短评）

**数据设计（用户建议采纳：评价单独建表，1 对多，ID 连接）**：
- **评价明细表**（独立，Step 11 建）：一行一条评价，字段 = `ratingId`、`pluginId`（→ 插件 ID，外键）、`anonUserId`（匿名身份证）、`stars`(1–5)、`comment`、`createdAt`、`installedVerified`(bool)、`status`(normal/flagged)。一件插件几百条评价都在这张表，不进菜单。
- **菜单里的 `ratings` 只是派生汇总**：`{ count, avg, distribution[5] }`，由明细表实时/定时重算，供店面直接显示——消费端零逻辑。

**规则（MVP）**：
- 1–5 星 + 可选一句话短评；
- **每插件每身份一票**（可改分，不可重复刷）；
- 展示**分布直方图**（几星各多少人）而非只给平均分 —— 平均分易被少数人带偏；
- 可选"装机验证"标记：若用户同意上报已装插件清单，该评分标注"装机用户"，权重更高（信任分层 +1）。

**防滥用（轻量，承认无人工审核）**：
- 匿名身份证天然防"无成本刷票"（每身份每插件一票）；
- 限流（如 1 分钟内最多 N 条提交）；
- 明确标注："评分未经审核，可能含刷分与情绪化评价"；
- 作者自评无法完全杜绝（作者也是用户）→ 用装机验证 + 分布展示缓解，不在第一版追求完美。

**对排行/推荐的联动**：
- 热度榜 = 综合分（GitHub 星 + npm 下载 + 评分），历史快照照常积累；
- Step 6 推荐算法可把评分作为输入之一。

## 五、架构影响：厨房从"只读"变"可收信"（关键决策点）

评分/反馈意味着**中央索引需要写通道**。三个候选（按成本排序，待定，不在第一阶段实现）：

1. **GitHub issue/表单**：反馈走 issue（免费、公开、可人工看）；评分数批由脚本自动汇总成 PR 合进共享数据。最廉价，但"提交评分"体验一般。
2. **Serverless 写接口**（如 Cloudflare Workers/某个免费函数）：店面直接 POST → 写入厨房数据仓。体验好，多一个小服务要维护与防滥用。
3. **延迟到"网站"形态一起做**：反正网站本质是"菜单的另一个窗口"，若未来做网站，写接口顺势挂它上面。

**决策建议**：阶段 A–C 只做"只读菜单"，反馈/评分全部排在**日报之后**（Step 5.5+），届时根据用户量与预算在 1/2/3 中选。这样厨房先以"零维护成本"跑起来，不被写通道拖累。

## 六、路线图落位（修订 04 的阶段划分）

- 阶段 A–C：不变（只读菜单 → 增量发现 → 开张）；
- 阶段 D（闭环）：自荐表单 + 反馈 issue 通道 + AI 报告共享缓存；
- 阶段 E（评价）：评分写通道（候选 1/2/3）+ 装机验证 + 综合热度榜。
- **验收**：评分机制上线后，抽查防刷有效（同身份同插件不可重复投票）、热度榜与直觉一致。
